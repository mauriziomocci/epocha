## Lookup 1 — F821 `Couple` undefined-name root cause

- **Decision**: not a runtime bug; type-annotation hygiene. Fix with a `TYPE_CHECKING` import block plus unquoting the annotations.
- **Evidence**: `epocha/apps/demography/couple.py` has `from __future__ import annotations` (line 13). `Couple` is defined in `epocha/apps/demography/models.py:12`. Inside `couple.py` it is imported only locally within functions (lines 42, 52, 166) to avoid a circular import, and referenced in string annotations at lines 158 (`-> "Couple"`), 178 (`list["Couple"]`), 319 (`list["Couple"]`), 369 (`"Couple | None"`). ruff F821 evaluates the string annotations and finds `Couple` unresolved at module scope.
- **Why not a runtime bug**: with `from __future__ import annotations`, all annotations are lazy strings and never evaluated at import/call time, so the missing module-level import has no runtime effect; the local imports cover the actual `Couple.objects` runtime use.
- **Fix**:
  ```python
  from typing import TYPE_CHECKING
  if TYPE_CHECKING:
      from epocha.apps.demography.models import Couple
  ```
  Then drop the now-redundant quotes (`-> Couple`, `list[Couple]`, `Couple | None`). This resolves F821 (Couple is name-resolvable for the checker) and the related UP037 quoted-annotation findings in this file, with no circular-import at runtime (the import is type-check-only).
- **Alternatives considered**: (a) module-level `from .models import Couple` — rejected, reintroduces the circular import the local imports were avoiding; (b) per-line `# noqa: F821` — rejected, hides the real fix and leaves the annotations unresolvable for type-checkers.

## Lookup 3 — Ordering constraint (formatter vs line-length)

- **Decision**: apply `line-length = 100` to `pyproject.toml` BEFORE running `ruff format`.
- **Rationale**: `ruff format` wraps code to the configured `line-length`. Running format under the old 88 then raising to 100 would leave code wrapped at 88 (still passing, but inconsistent and wasteful); running format under 88 then re-checking at 100 wastes a pass. Setting 100 first makes a single format pass produce 100-width code that satisfies both `ruff format --check` and the E501 budget.
- **Alternatives considered**: format-first-then-raise — rejected (double work, inconsistent width).
