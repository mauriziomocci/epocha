## Key decisions and why

Do not relitigate these; they are settled and recorded in code docstrings.

- **D1 — same-tick double death** is handled inside `couple.py:dissolve_on_death` (falls back to a couple already dissolved at the same tick), NOT duplicated into `inheritance.py`. Signature unchanged; threading batch state through the caller was explicitly rejected.
- **D5 — the derived-formula evaluator** walks an AST node whitelist, resolves names only against the caller's `symbols` dict, and never calls `eval()`. **The whitelist IS the security property (SC-006) — never widen it to make a test pass.**
- **T003 superseded — the whitepaper §4.1 update is consolidated at closure (T043)**, not done piecemeal. §4.1 is `frozen-at-commit` and re-pinned only at merge; editing its prose earlier would describe code ahead of its declared commit. The D1 fix is an integration detail that does not change the scientific model, so the doc-sync escape clause applies. Decided by the user.
- **`resolve_heirs` returns `dict[str, list]`, not a flat list.** The plan sketched a list; the categories are required downstream (primogeniture needs children in birth order, shari'a must tell spouse from children). There is deliberately **no "government" key** — every category being empty IS the treasury fallback.
- **`distribute_estate` persists nothing.** Returning a pure id-keyed allocation mapping is what makes the conservation invariant assertable in isolation. Conservation is enforced by giving the LAST heir in deterministic order `total - sum(others)`, so the allocation sums exactly.
- **Loans transfer to the banking system, never cancelled.** The design spec contradicts itself in one sentence (`docs/superpowers/specs/2026-04-18-demography-design-it.md` line 787 and its FAQ ~line 1374) saying both "transfers to banking and keeps being serviced" and "silently cancelled at MVP". Cancelling an active credit would destroy value and break the conservation invariant this user story exists to protect. Flagged for the audit.
- **Class ladder reused, not duplicated**: `_CLASS_RANK` is imported from `world/stratification.py` (the canonical definition) and extended locally with `enslaved` at the bottom, because the model admits that label but stratification never assigns it and patrilineal inheritance must transmit servile status.
- **Deterministic iteration everywhere.** Never iterate a Python `set` over trait or heir names: set order depends on the process string-hash seed and would silently break bit-for-bit reproducibility. Heritability-table order, then lexicographic; heirs oldest-first by `birth_tick` with `id` as tie-break.
- **The module never persists.** Every `inheritance.py` function mutates its argument and leaves `.save()` to the caller, so the Plan 4 orchestrator can compose them in one transaction. Keep this contract in `migration.py` too.
- **`evaluate_emergency_flight` takes the starvation counter as an argument** — a deliberate, user-approved deviation from the signature `plan.md` declares. Decided 2026-07-20 after verifying exhaustively that `consecutive_ticks_under_subsistence`, which the design names as one of the three simultaneous flight conditions, exists nowhere: there is no such field on `Agent`, no per-agent wealth history to derive it from (`Agent.wealth` carries only the current value), and `PopulationSnapshot` is aggregated per simulation. It is by definition a cross-tick counter, so it must persist somewhere. Adding a field would have broken SC-005, the approved spec's zero-migration success criterion that T042 enforces; hiding it in `Agent.conditions` or `personality` would have been the JSON-blob-where-relational-serves anti-pattern the project's own design process names as a smell. Passing it in keeps this plan at zero migrations, keeps the module pure per decision D3, and places the persistence question where it belongs — Plan 4, which owns tick-loop state and may legitimately migrate. **Plan 4 must therefore create the storage and feed this argument**; until it does, emergency flight cannot fire in a live run, which is consistent with demography not being wired at all yet.
- **T043 must not claim that all five succession rules are in use.** Verified against the template files at T041 on 2026-07-20: of the five implemented rules, the shipped era templates declare only three. `pre_industrial_christian` uses `primogeniture`, `pre_industrial_islamic` uses `shari'a`, and `industrial`, `modern_democracy` and `sci_fi` all use `equal_split`. **`matrilineal` and `nationalized` are declared by no template at all** — they are implemented and unit-tested in isolation (`TestDistributeEstateMatrilineal`, `TestDistributeEstateNationalized`) but reachable at runtime only through a purpose-built scenario override. §4.1 may therefore state that five rules are implemented, but must not imply that five eras exercise them; writing otherwise would put a claim in the paper that the shipped data contradicts. The same care applies to the class rules, where four distinct values cover the five eras (`patrilineal_rigid` twice, then `clark_regression`, `becker_tomes_elasticity_0.4`, `meritocratic`), and to the estate-tax rates, which are 0.0 for both pre-industrial eras and for sci-fi, 0.15 industrial and 0.40 modern.

## Open questions — the phase-6 audit (T046) must rule on these

None blocks T024-T045. All are documented in code; none was resolved by guessing.

1. **`era_mean` / `era_sd` interim defaults (0.5 / 0.15).** The design wants them estimated from the tick-0 population and frozen; that machinery is Plan 4 and no template declares the data. The code reads a template noise spec first and falls back to named, documented, tunable constants.
2. **`mental_health_baseline` vs `mental_health`.** The template inherits the former (lands in `personality`); the model has a distinct scalar `mental_health`. Confirm the separation is intended and decide whether `Agent.mental_health` should be initialised from the inherited baseline at birth.
3. **Siblings broadened.** The spec names the mother's FK only; the implementation matches either parent, so paternal half-siblings are found. Justified because the next fallback is the treasury, and paternal siblings are the relevant ones under patrilineal primogeniture.
4. **`enslaved` ladder extension.** `_CLASS_RANK` in stratification has five classes; the model documents six. A future change to those five keys would silently desync the local extension — re-verify at every audit.
5. **Loan spec contradiction** resolved in favour of banking transfer (never cancellation) on conservation grounds. Confirm.
6. **Shari'a residuary cascade simplified** to the same depth as primogeniture (children → siblings → spouse absorbs). Documented as this module's own extension, explicitly NOT attributed to Powers 1986.
7. **`rho` divergence.** The design spec lists education-regression rho as 0.5 / 0.42 / 0.35 / 0.25; the templates carry 0.5 / 0.4 / 0.4 / 0.2. Code reads the template (correct at runtime), but spec and data should be reconciled.
8. **`inherit_trait` with BOTH parents unknown** raises an opaque `TypeError`. Out of contract (at least one parent required, documented), but the audit may want an explicit guard.
9. **No representation per stirpes.** Surfaced during T028 and verified against the code on 2026-07-20: `_resolve_children_heirs` matches only direct parentage FKs, and `_resolve_extended_family_heirs` walks UP to the grandparents and back DOWN to aunts/uncles and cousins — so the deceased's OWN grandchildren are unreachable by any category of the ladder, which the templates fix as `spouse -> children -> siblings -> extended_family -> government`. When every child predeceased the parent, the estate therefore skips the grandchildren entirely and falls to siblings, extended family, or the treasury. Real succession systems almost universally admit representation (a grandchild takes the dead parent's share, *per stirpes*), so this is a substantive simplification of the model, not an implementation gap: the code faithfully implements the CONVERGED design, and the design never names grandchildren. The audit must rule on whether the simplification is acceptable and, if so, document it as such in §4.1; adding a category would reopen a converged design and was deliberately NOT done here.
10. **`ESTATE_TAX_CURRENCY_CODE = "USD"` is an undeclared placeholder.** `process_inheritance_batch` (T029) must pass a currency code to `apply_estate_tax`, which uses it as the treasury dict key. No simulation-level primary-currency field exists for the simplified economic tier that `Agent.wealth` belongs to, and `economy.property_market._get_primary_currency` returns `None` when a simulation carries zero `Currency` rows, so the constant hardcodes `"USD"` and documents itself as an MVP simplification. It is functionally inert — an arbitrary bookkeeping label, exactly as every existing `apply_estate_tax` test already treats it — but it denominates a pre-industrial or feudal treasury in dollars, which the paper cannot defend on its face. The audit should decide between an era-neutral label, resolving the code from the era template, or accepting and documenting it explicitly in §4.1.
11. **The Harris-Todaro operational variant is dimensionally inconsistent.** Surfaced while preparing T033 and verified against the design spec on 2026-07-20. The design fixes the expected-gain formula as `E[gain_j] = (1 - unemployment_j) * wage_j - wage_current - distance_cost_j` (design spec line 826), and separately fixes `distance_cost` as `ceil(distance_km / (walking_speed_km_per_day * tick_duration_days))` — a COUNT OF TICKS, which the design's own worked example labels explicitly as "Costo distanza in tick: Paris 0, Lyon 3, Countryside 5" (line 811). The first two terms are a currency rate (the example reports them in "LVR/tick"), so the formula subtracts a duration from a rate. The worked example does not expose the error only because it computes the gain for Paris, whose distance cost is zero: reconstructing it gives 0.92 * 90 - 78 = 4.8, matching the stated "+4.8 LVR/tick" exactly, with the third term absent. For Lyon, three ticks of travel would be subtracted directly from a per-tick wage. The implementation follows the design verbatim, as this plan executes rather than reopens it, and states the inconsistency in its own docstring rather than silently papering over it. The audit must rule: either monetise the distance cost (the natural reading is forgone earnings, `distance_cost_ticks * wage_current`, which restores dimensional consistency and preserves the example), or declare an explicit scaling of one currency unit per tick of travel and justify it. This is a GOLDEN RULE matter — a published formula whose units do not balance is not defensible in the paper.
12. **"Zone stability" in the migration outlook is not per-zone.** Surfaced while preparing T034 and verified against `epocha/apps/world/models.py` on 2026-07-20: `Government` is a `OneToOneField` to `Simulation`, so exactly one government — and one `stability` scalar — exists per simulation. The design's worked example nonetheless shows stability differentiated BY zone ("Paris crisi (0.3), qui stabile (0.7), Countryside stabile (0.6)", design spec line 812), and T034 names `Government.stability` as the source. Under the current schema every zone therefore reports the SAME number, which makes the column useless for the zone comparison that is its entire purpose: an agent weighing Paris against the countryside sees no difference on the axis the design intends to drive flight from unstable regions. The same conflation already exists in merged code — `epocha/apps/demography/context.py:41` documents the value as "zone stability (Government.stability)" while reading a simulation-wide scalar — so this is a pre-existing modelling gap that T034 inherits rather than introduces. No per-zone stability field exists anywhere in the schema. This plan does NOT add one: SC-005 fixes zero migrations, and inventing a proxy would be exactly the kind of silent invention the escalation rule forbids. T034 therefore reports the simulation-wide value for every zone and says so explicitly in its docstring. The audit must rule on whether a per-zone stability signal is required for the migration model to mean what §4.1 will claim it means, and if so, schedule it as its own work item.
13. **The household arrives before the agent who decided to move.** Surfaced at T035 and verified against both implementations on 2026-07-20. `coordinate_family_migration` moves the partner and the minor children by assigning `mover.zone = target_zone` directly, so they arrive instantly, in the tick of the decision — which is exactly what the design asks for ("Partner e tutti i figli con `age < adulthood_age` migrano con lui nello stesso tick", design spec line ~830) and what T035's own acceptance criterion demands. The deciding agent, however, moves through `agents/movement.py:execute_movement`, which explicitly supports partial multi-tick journeys: an agent who cannot reach the zone centre this tick advances along the straight-line path and arrives later. The two mechanisms therefore disagree about how long a journey takes. A household migrating to a zone three ticks away has its spouse and minor children materialise at the destination immediately while the parent who made the decision is still in transit — minors unaccompanied in a new zone for three ticks, which the orphan-caretaker model would not even notice because both parents are alive. The same tension is visible inside the design itself, which asks for same-tick family movement while modelling journey length in ticks through `distance_cost`. Neither implementation is unfaithful to its instructions, so nothing was changed. The audit must rule on whether the household should travel with the decider (and inherit multi-tick journeys, mood and health costs), or whether same-tick family arrival is an accepted abstraction to be documented as such in §4.1.
14. **`get_seeded_rng` mixes the database primary key into the seed, and its own docstring denies it.** Found at T040 and verified directly against `epocha/apps/demography/rng.py` on 2026-07-20. The module docstring opens by promising "publication-grade reproducibility" and states that each stream is "derived from a deterministic hash of (simulation.seed, tick, phase)" — `simulation.id` is never mentioned. Line 41-42 builds the key as `f"{simulation_id}:{base_seed}:{tick}:{phase}"`, so the primary key IS part of the hash. The consequence is not cosmetic: anyone reproducing a published result on a fresh database gets a different `simulation.id`, therefore different RNG streams, therefore different demographic outcomes, despite using the seed the paper declares. This is an INDEPENDENT second reason to re-examine the bit-identical reproducibility claim, distinct from the already-tracked problem that the world and agents are generated by an unseeded LLM — that one concerns non-deterministic INPUTS, this one concerns the RNG stream itself diverging on identical inputs. The behaviour is deliberate rather than accidental, and the economy twin settles it: `epocha/apps/economy/rng.py` builds the same key and its docstring states the scheme accurately as `sha256 over "{simulation_id}:{seed}:{tick}:{phase}"`, having additionally survived a Round 7 re-audit that added the `"economy:"` namespace so the two apps do not derive identical streams for a shared phase label. So the defect is narrower and clearer than it first appears: the demography docstring is simply inaccurate about a deliberate design, while the economy one is correct. What NEITHER docstring records is the consequence — that keying on a database primary key makes a fresh-database re-run of a published seed diverge — and that consequence is what the paper's reproducibility notes must carry. `rng.py` was deliberately NOT changed here: it is merged, audited infrastructure consumed by mortality, fertility and couple as well, and altering seed derivation would silently invalidate every existing seeded expectation across the demography suite. A permanent test pins the current coupling so the behaviour cannot drift unnoticed: `TestGetSeededRngSimulationIdCoupling` in `epocha/apps/demography/tests/test_inheritance.py`. The audit must rule on which of the two is authoritative, and the answer belongs in the whitepaper's reproducibility notes, not only in a docstring.
